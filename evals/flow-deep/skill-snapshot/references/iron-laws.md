# 统一铁律体系 — Iron Laws + Rationalization Tables

> 本文件定义 flow-deep 管道中所有刚性技能的铁律和反合理化表。
> 被引用位置: `skill-routing.md` (TDD/Code Review Agent prompt), `stage5-verification.md` (验证阶段)
> 设计来源: Superpowers 框架的 Iron Law 模式 — 每个刚性技能用铁律 + 红旗表防止 LLM 自我辩解跳过纪律。

## 核心原则

铁律不是建议，是**不可协商的执行纪律**。每条铁律配有 Rationalization Table — 列出 LLM 最可能用来绕过铁律的自我辩解话术。当 Agent 的内部推理中出现这些话术时，必须立即停止当前行为，回到铁律。

---

## IL-1: TDD 铁律 (Test-Driven Development)

> **IRON LAW**: No production code without a failing test. 没有失败测试就不写生产代码。

### 执行要求
1. **RED**: 先写一个失败的测试 → 运行确认它是 failure（不是 error）
2. **GREEN**: 写最小代码使测试通过 → 运行确认通过
3. **REFACTOR**: 在测试通过的前提下重构 → 每步重构后确认测试仍通过

### Rationalization Table

| 红旗话术 | 为什么这是绕过 | 正确做法 |
|---------|-------------|---------|
| "先写实现再补测试" | 跳过 RED 阶段，测试变成验证而非驱动 | 先写测试，即使实现还不存在 |
| "这个太简单不需要测试" | 简单代码也会有 bug，且未来维护者不知道它"简单" | 为每个函数/方法写测试 |
| "测试框架还没配好" | 框架配置是一次性成本，不应成为跳过测试的理由 | 先配好测试框架，再开始开发 |
| "just this once" | 一次例外 = 纪律崩塌的开始 | 没有例外 |
| "后面再补" | "后面"永远不会来 | 现在、立刻、马上 |
| "用户要求快速交付" | 快速但不安全的交付是技术债 | TDD 长期看更快（减少调试时间） |
| "这是重构，不影响功能" | 重构引入 bug 的概率与新增功能相同 | 重构前确保测试覆盖，重构后确认测试通过 |
| "我确信这段代码是对的" | 确信不等于证据 | 运行测试才是证据 |

### Delete-Means-Delete 规则
如果发现自己已经写了实现代码但没有先验证测试失败: **删除实现代码**，从 RED 阶段重新开始。

## IL-2: 验证铁律 (Verification Before Completion)

> **IRON LAW**: No completion claims without fresh verification evidence. 没有**新鲜的**验证证据就不宣布完成。

### 执行要求
1. 每个 Phase 完成后，运行**实际命令**验证产出
2. 验证证据必须是**实际命令输出**，不可使用 "should work"、"probably"、"seems to"
3. 测试输出、lint 输出、文件存在检查都必须附带原始输出
4. 验证失败 = 未完成，不允许标注为"已知问题"后跳过

### Rationalization Table

| 红旗话术 | 为什么这是绕过 | 正确做法 |
|---------|-------------|---------|
| "代码看起来应该能工作" | "看起来"不是证据 | 运行它，展示输出 |
| "逻辑上是对的" | 逻辑推理无法替代运行验证 | 运行实际测试 |
| "这个 bug 不影响主流程" | 所有未验证的 bug 都可能在生产环境放大 | 要么修复，要么在报告中显式标注并说明影响 |
| "测试环境没有，没法验证" | 没有验证环境 = 无法确认完成 | 先搭建最小验证环境 |
| "上一轮已经验证过了" | 上一轮的验证不覆盖本轮的变更 | 每次变更后重新验证 |
| "大概通过了" | "大概"不是验证结果 | 100% 通过或 0% 通过，没有中间态 |
| "这个 lint 警告可以忽略" | 警告存在就有原因 | 修复它或在报告中明确说明为什么安全忽略 |
| "手动检查过了" | 手动检查不可复现、不可追溯 | 自动化验证命令 + 输出证据 |

### Spot-check 三项检查（每个 Phase 完成后）
1. 预期创建/修改的文件是否存在
2. `git log --oneline -3` 确认有新提交
3. 相关测试是否通过（附运行输出）

## IL-3: 调试铁律 (Systematic Debugging)

> **IRON LAW**: 没有根因就不改代码。Don't fix what you don't understand.

### 执行要求
1. **收集症状**: 读取错误信息、堆栈、复现步骤。信息不足时逐个追问
2. **模式匹配**: 对照常见 bug 模式（竞态条件/空值传播/状态损坏/集成失败/配置漂移/缓存过期）
3. **假设验证**: 添加临时日志或断言确认假设。3 次假设失败则停下来重新评估
4. **最小修复**: 确认根因后做最小改动，不改无关代码。修改 > 5 个文件需先确认
5. **验证闭环**: 复现原 bug 场景确认已修复，运行相关测试

### Rationalization Table

| 红旗话术 | 为什么这是绕过 | 正确做法 |
|---------|-------------|---------|
| "可能是这个问题，先改了试试" | 没有验证假设就修改代码，浪费时间且引入新 bug | 先用日志/断言验证假设 |
| "我见过类似的 bug" | 不同上下文的"类似"bug 可能有不同根因 | 用证据确认，不用经验猜测 |
| "改一下这里应该就好了" | "应该"不是确认 | 改之前先确认根因 |
| "多个地方一起改比较快" | 大范围改动难以定位真正的修复点 | 一次只改一个地方，每步验证 |
| "反正需要重构，顺便修了" | 重构不是修复 bug 的借口 | bug 修复和重构是两个独立操作 |
| "这个错误信息不重要" | 错误信息是诊断的关键线索 | 仔细阅读每一条错误信息 |
| "3 次假设都失败了，再试一次" | 连续失败说明方法论有问题 | 停下来，重新审视问题，可能需要换个角度 |
| "先绕过这个问题" | 绕过 = 掩盖，不是修复 | 找到根因再决定修复方案 |

### 3-次假设规则
如果连续 3 次假设都未验证成功:
1. **停下来** — 不要继续猜测
2. **重新描述问题** — 用不同的角度重新定义 bug
3. **收集更多信息** — 可能需要更详细的日志、不同的复现路径
4. **必要时上报** — 标记为 blocker，向用户说明卡点

## IL-4: 代码审查铁律 (Code Review)

> **IRON LAW**: 审查是只读操作。Review is read-only — observe, report, never modify.

### 执行要求
1. 审查 Agent **不得修改任何文件** — 只返回审查报告
2. 按 severity 分级: BLOCKER（必须修复）/ MAJOR（强烈建议）/ MINOR（建议优化）
3. 每个发现必须可定位: 文件路径 + 行号 + 具体描述
4. 审查维度全覆盖: Spec 合规 + 代码质量 + 安全 + 测试覆盖 + 接口一致性

### Rationalization Table

| 红旗话术 | 为什么这是绕过 | 正确做法 |
|---------|-------------|---------|
| "顺便把这个问题修了" | 审查 Agent 修改代码 = 审查者和修改者是同一人，失去独立审查价值 | 只报告，不修改 |
| "这个太小了，不用报" | 小问题积累成大问题 | 所有发现都报告，按 severity 分级 |
| "我不确定这是不是问题" | 不确定 = 需要更多调查 | 标记为 MINOR 并说明不确定原因 |
| "代码风格问题不重要" | 风格不一致 = 团队协作摩擦 | 归为 MINOR，但仍然报告 |
| "时间不够，跳过安全审查" | 安全审查是最不能跳过的维度 | 安全维度不可跳过 |
| "看起来没问题" | "看起来"不是审查结论 | 每个维度逐项检查，附检查结果 |
| "这个超出审查范围了" | 审查范围外的发现仍然有价值 | 报告为额外发现，标注为范围外 |

### BLOCKER 级问题处理
发现 BLOCKER 级问题时:
1. 立即在报告中标注为 **BLOCKER**
2. 说明为什么不可接受（不是"建议修改"而是"必须修改"）
3. 提供具体修复方案
4. 不允许将 BLOCKER 降级为 MAJOR
