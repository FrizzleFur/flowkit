一句话总览 graph engineering = 当团队从「人提示智能体」转向「其他东西代表人类提示智能体」[03:18]， 人被抬到实际工作之上的一层 [05:33]，可靠性成为采用前提 [05:44]—— 此时把 SOP 画成 control graph（节点、边、状态 [06:19]），让智能体循着图跑，就是让循环可靠、可复利的方法论。 它可以用代码实现，也可以只是一份文档化的 SOP [09:15]。

两种模式汇合处：control graph 的位置

共同结果两种模式都让人类处于实际工作之上的一层，不再全程盯执行智能体的步骤与检查点[05:31]

四个设计原则 确保智能体真正遵循 SOP [11:39]

#原则视频给出的判断与做法锚点
1 何时拆智能体节点 技术上可以把所有 SOP 塞进一个智能体，模型越强越可能直接完成 [11:47]；但要理解模型边界：模型再强，自我验证自己的工作都做不好——所以验证器通常是独立的智能体节点 [12:03]；OpenAI 与 Anthropic 的研究表明复杂任务需要一个深思熟虑的规划智能体 [12:10]；另考虑什么可并行 [12:24]、什么适合更强/更弱的模型 [12:28] [11:42]
2 合理时用代码（脚本） 提高可靠性、跑得更快、减少不必要的错误 [12:41]。常见场景：复杂数据获取（与其让智能体调多个 API 整合，不如写脚本）[12:54]、常见数据分析 [13:05]、直接把 server 跑起来 [13:09]、让智能体具备评估结果 / 端到端测试的能力 [13:14] [12:38]
3 定义输入与输出 每个智能体节点都要定义输入和输出，确保每个节点的边界非常清晰 [13:24] [13:18]
4 状态放哪 无论哪种实现，都需要让不同智能体快速理解当前工作状态 [13:35]；最简单的方法：用一个 markdown 文件记录最新状态 + 每个智能体每次运行的日志 [13:43] [13:29]
方法论收口（任何想让它重复、可靠执行的任务都适用）[13:55] 规划出 SOP、想清楚所有步骤 [14:00] → 按设计模式把内容分组到不同节点和边 [14:04] → 定义一个能记录状态的产出文档 [14:08]。 两种路线的区别只在输出物：LLM 即 graph 产出一个 skill，代码即 graph 产出一段可运行 JS [14:17]。
