# Fallback Protocol - 退回 Plan 协议

> 本文件由 flow / flow-deep SKILL.md 共同引用。定义 Stage 4 执行过程中的异常处理和退回 Plan 协议。
> 核心理念: 失败时先退回 Plan，不要硬推——避免连锁错误。

## 概述

在 Stage 4（执行）过程中遇到意外时，通过结构化的异常分类和退回协议，避免"就地修"导致的连锁错误。退回 Plan 需要用户手动触发和确认。

## 异常分类决策树

```
遇到意外/错误
    │
    ▼
问: "这是 plan 的执行偏差，还是 plan 本身的假设有误？"
    │
    ├── 执行偏差 → 直接修，继续执行
    │   - typo、小遗漏
    │   - lint 错误
    │   - 测试中的小断言差异
    │   - 配置项遗漏（不影响架构）
    │
    └── Plan 假设有误 → 触发 Plan Fallback 协议
        - API 版本不兼容
        - 依赖冲突
        - 架构设计问题
        - 文件结构与 plan 预期不符
        - 需要 plan 未涵盖的新模块
```

```
  遇到意外/错误
       │
       ▼
  异常分类决策
       │
  ┌────┴─────────────────┐
  ▼                      ▼
执行偏差              Plan假设有误
(可直接修)            (需退回Plan)
  │                      │
  ▼                      ▼
修复 → 继续执行     Plan Fallback协议
- typo                   │
- lint错误               ▼
- 小遗漏             1.暂停执行
                     2.记录状态
                     3.分析影响
                     4.更新plan
                     5.用户确认
                     6.继续执行
```

## Plan Fallback 操作步骤

### 步骤 1: 暂停执行

- 立即停止当前 Phase 的执行
- 不做任何"顺便"的修复
- 保留当前状态（不回滚，不推进）

### 步骤 2: 记录状态

在 progress.md 中添加 Fallback 记录:

```markdown
## Fallback #[N]

**触发时间:** [时间戳]
**触发 Phase:** [Phase 名称]
**触发 Task:** [Task 名称]
**失败原因:** [具体描述]

**Plan 假设错误:**
- Plan 假设: [原来的假设]
- 实际情况: [发现的事实]
- 影响范围: [受影响的后续步骤]

**执行状态:**
- [x] Task 1.1: 已完成 ✅
- [x] Task 1.2: 已完成 ✅
- [ ] Task 1.3: 失败点 ❌ ← 当前位置
- [ ] Task 2.1: 待执行（可能受影响）
- [ ] Task 2.2: 待执行（可能受影响）

**需要重新规划的步骤:**
- [ ] Task 1.3: [需要修改的原因]
- [ ] Task 2.1: [需要修改的原因]
```

### 步骤 3: 分析影响

- 确定哪些已完成的步骤仍然有效
- 确定哪些待执行的步骤受影响
- 评估是否需要回滚已完成的步骤

### 步骤 4: 更新 Plan

- 只修改受影响的步骤
- 保留已验证的步骤不变
- 更新后的 plan 需要重新满足 plan-quality.md 的质量标准
- 如果受影响范围 > 50% 的步骤，考虑完全重写 plan

### 步骤 5: 用户确认

向用户展示:
1. 失败原因和 Plan 假设错误
2. 受影响的步骤范围
3. 更新后的 plan（标记变更部分）
4. 是否需要回滚已完成的步骤

```
Plan Fallback 报告:

失败原因: JWT 库版本不兼容
  - Plan 假设: 使用 jwt@v4 API
  - 实际情况: 项目锁定在 jwt@v3

受影响步骤:
  Task 1.3: 需要重写（API 不兼容）
  Task 2.1: 需要调整（依赖 Task 1.3 输出）

已验证步骤（保留）:
  Task 1.1: ✅ auth middleware
  Task 1.2: ✅ 路由配置

更新后的 Plan:
  [展示变更]

是否按更新后的 plan 继续?
```

### 步骤 6: 继续执行

用户确认后:
- 从更新后的当前 Task 继续执行
- 不回退已完成的步骤（除非用户要求）
- 更新 progress.md 中的状态

## 半自动模式说明

- 异常分类由 Claude 自动判断（执行偏差 vs Plan 假设有误）
- 执行偏差: 自动修复，继续执行
- Plan 假设有误: 暂停，展示分析结果，等用户确认退回
- 用户也可以在任何时候主动触发 Plan Fallback（通过指令）

## 与 Plan Review 的关系

| 场景 | 机制 | 触发时机 |
|------|------|---------|
| 执行前审查 | Plan Review (Stage 3.5) | Stage 3 完成后 |
| 执行中异常 | Plan Fallback (Stage 4) | 执行中遇到 Plan 假设错误 |

两者互补:
- Plan Review 是"预防性"审查——在执行前发现假设错误
- Plan Fallback 是"反应性"退回——在执行中发现假设错误

## 注意事项

- 每次退回 Plan 都会记录在 progress.md 中，便于复盘
- 如果同一 Phase 触发 2 次 Fallback，建议退回 Stage 2 重新思考
- Fallback 不回滚 git 提交——已提交的代码保留，新 plan 在此基础上调整
- 半自动模式: Claude 建议退回，但需要用户确认
