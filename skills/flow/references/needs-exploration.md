# Stage 1.5: 需求探索

> 由 flow/flow-deep 共享。在 Prompt 优化后，按用户认知状态走不同追问路径。

## 术语澄清

- **grill-me** — mattpocock 的 user-invoked 入口 skill（独立调用，无代码库时用）
- **grilling** — mattpocock 的 model-invoked 原语（被入口或 flow-deep 调用）
- **Grilling 模式** — flow-deep Stage 1.5 内的范式（可调用 grilling 原语承载），不等同于 grill-me 入口

## 触发条件（双路径）

Stage 1 完成后，按用户的认知状态选择触发路径。**"主干明确"看的是有没有实现路径 / 技术选型，不是"不确定项少"**——主干明确 + 细节未定（如"用 Strategy 重构支付，支持哪些币种待定"）仍属路径 A。

**路径 A：主干明确 → 轻量 Grilling**

任务表述已含具体实现路径 / 技术选型 / 明确边界（如"用 Strategy 模式重构支付，要兼容旧 API"）。**不依赖"3+ 不确定项"**——这类任务即使不确定项 < 3 也触发，把残留的关键决策点快速确认掉，避免被跳过条件过滤、Grilling 沦为死代码。

**路径 B：模糊想法 → 选项式**

任务表述只有效果目标 / 痛点、方案未定，且存在以下任一情况：

- 技术方案描述模糊（如"优化性能"但无具体指标）
- 业务逻辑不确定（如"支持多币种"但未指定哪些币种）
- 影响范围不清（如"重构认证系统"但未说明边界）
- 存在 3 个以上不确定的关键决策点

**参考**: superpowers:brainstorming 的需求探索模式（路径 B 可借鉴）

## 行为

按触发条件判定的路径执行对应模式。

### Grilling 模式（路径 A，主干明确型）

借鉴 Matt Pocock 的 grilling 范式。核心是"决策归用户、事实归代码、一次一问、深度优先"：

1. **Facts vs Decisions 分离** — 对每个待澄清点先判断性质：
   - **事实**（读代码 / 配置 / 文档能确定的，如"现在用的哪个支付 SDK"）→ 不问用户，自行探查消解，把结论带回任务表述
   - **决策**（需要用户拍板的取舍，如"是否兼容旧 API"）→ 上浮给用户
   - 这一步能消解大部分"其实读代码就知道"的问题，避免用户被问爆
2. **一次一问 + 深度优先** — 沿决策树逐分支追问，每次只抛一个问题，等回答再进下一个。一次抛多个会令人困惑（bewildering）。
3. **每问附推荐答案** — 对有明显优劣的决策，给出推荐项 + 一句理由，用户可一键认同或反驳。推荐是加速器，不是替代器。
4. **决策归用户** — 用户反驳推荐时，记录其理由（理由对后续 spec 比一句"yes"更有价值）。
5. **共享理解门禁** — 追问持续到"双方对方案的理解一致"为止，再进入下一步，不提前收束。
6. **防拷打三律**（2026-08-21 吸收自苏格拉底提问法）— 追问的价值要实时可见，否则沦为审讯：
   - **增量披露** — 每次提问前用一句话说明"上一条回答让你更新了什么判断"，用户能看到追问在收敛而非空转；
   - **改变结论判据** — 只问"答案可能改变结论"的问题，对结论无影响的好奇心一律按住；
   - **显式停止** — 信息足够时立刻收束，不凑满问题数（与第 5 条门禁互补：门禁说"何时才算够"，三律说"别超过必要"）。

若已安装 mattpocock skills，可直接调用 `/grilling` 原语（或 `/grill-with-docs` 同时沉淀 CONTEXT.md / ADR）承载追问循环。

### 选项式（路径 B，模糊想法型）

1. **不确定项识别**: 分析优化后的任务表述，列出关键不确定项（最多 5 项）
2. **评估明确度**: 对每个不确定项评分 0-10（明确度 < 7 的需要追问）
3. **主动追问**: 对明确度 < 7 的不确定项，使用 AskUserQuestion 向用户确认:
   - 每个问题最多提供 4 个选项 + 自由输入
   - 选项应包含合理默认值（标注 Recommended）
   - 问题应具体而非笼统（"需要支持哪些币种？" 而非 "还有其他需求？"）
4. **合并结果**: 将用户回答合并到任务表述中，生成"明确后的任务表述"

> 选项式仍含 choice architecture 风险（AI 供选项 + 推荐）。缓解：每个推荐附一句理由、显式鼓励"自由输入"、选项数 ≤ 4。模糊想法阶段不可避免，但路径 A 不受此风险。

### 收束（两模式共用）

5. **记录**: 写入 findings.md 的"需求探索"章节（Grilling 模式额外记录：被消解的事实项、用户反驳推荐的决策及其理由），结构按「问诊六件套」（2026-08-21 吸收自苏格拉底提问法）：
   - ① 用户最初问的问题 → ② 真正想解决的问题 → ③ 已确认的事实 → ④ 仍未验证的假设 → ⑤ 最可能改变结论的关键变量 → ⑥ 一个准确、具体、可继续行动的新问题
   - 六件套让后续 Stage 拿到的是"澄清后的新问题"而非散落的问答记录；⑥ 直接作为 Stage 2 深度思考的输入

## 示例

```
任务: 重构支付系统，支持多币种

不确定项:
1. 具体币种范围（明确度: 3/10）→ AskUserQuestion
2. 支付方式范围（明确度: 5/10）→ AskUserQuestion
3. 向后兼容要求（明确度: 8/10）→ 无需追问

AskUserQuestion:
Q1: "需要支持哪些币种？"
  - CNY + USD + EUR + JPY（推荐）
  - 仅 CNY + USD
  - 自由输入

Q2: "需要支持哪些支付方式？"
  - 支付宝 + 微信 + 信用卡（推荐）
  - 仅支付宝 + 微信
  - 自由输入
```

## 跳过条件

既非主干明确（任务表述无实现路径 / 技术选型 / 明确边界），且不确定项 < 3 且所有明确度 >= 7 —— 任务已足够清晰，无需探索。
